## 2. The eight questions

The set was chosen so that each query exercises a different access pattern. A
first draft was discarded because several "obvious" stock queries (reorder
alerts, dead stock, duplicate payments) return zero rows on this deliberately
clean dataset — an empty result set tells you nothing about the planner.

| # | File | Business question | Shape | Rows out |
|---|---|---|---|---|
| Q01 | `q01_daily_trading.sql` | Daily revenue for the last 30 days | date range + aggregate | 30 |
| Q02 | `q02_top_products_90d.sql` | Top 20 products by revenue, last 90 days | date range → 4-way join → group | 20 |
| Q03 | `q03_latest_payment_30d.sql` | Latest payment attempt for every recent order | `LATERAL … LIMIT 1` per order | 8,023 |
| Q04 | `q04_customers_never_ordered.sql` | Active customers who never converted | anti-join | 883 |
| Q05 | `q05_stock_cover.sql` | Days of stock cover per SKU, warehouse 1 | ledger aggregate + join | 25 |
| Q06 | `q06_category_tree_revenue.sql` | Revenue by top-level category | recursive CTE + roll-up | 8 |
| Q07 | `q07_customer_ltv.sql` | Top 100 customers by lifetime spend | high-cardinality group by | 100 |
| Q08 | `q08_carrier_delivery.sql` | Carrier on-time performance | filtered aggregate | 5 |

Two details that matter for repeatability:

- **Queries 1, 2, 3, 5 and 8 pin their window to `2026-10-20`**, the day after
  the newest order in the seeded data. `CURRENT_DATE` would drift and the
  numbers below would stop reproducing after the assignment deadline.
- **Q03 is written the way a developer would naturally write it.** `LATERAL`
  with `ORDER BY … LIMIT 1` is the obvious way to ask for "the latest payment
  per order". The section 7 shows what that costs without an index.

## 3. How the measurements were taken

| Setting | Value |
|---|---|
| Server | PostgreSQL 16.15, portable Windows build, `shared_buffers` 128 MB (default) |
| Data | 1,354,231 rows, 208 MB, generated by `seed.py` with a fixed seed |
| Iterations | 1 discarded warm-up pass, then 3 measured runs (median reported) |
| Session settings | `max_parallel_workers_per_gather = 0`, `jit = off` |
| Before each phase | `VACUUM (ANALYZE)` |

Three choices deserve an explanation, because each one changes the numbers:

**The warm-up pass is not optional.** On the first attempt the "after" plans
looked better than they were, because creating seven indexes had read every
table into memory. The before/after comparison was measuring the cache, not the
planner. One discarded pass at the start of each phase removes that bias; the
first capture was thrown away and redone because of it.

**Parallel query is off for the measurement.** Parallel workers report buffer
counts per worker, so the `Buffers:` line of a parallel plan does not describe
the whole query. Since buffer counts are the most reliable signal on a shared
laptop, the measurement is serial. Production would leave parallelism on and be
faster than these numbers, in both phases.

**The machine is a laptop and the variance is real.** Q03's three runs took
124 s, 148 s and 192 s; Q02's took 249 ms, 402 ms and 441 ms. The median is
reported, the raw runs are kept in `results/timings.csv`, and no conclusion
below rests on a difference smaller than that spread. "Pages" is
`shared hit + shared read`, i.e. how many 8 kB pages the plan touched, which is
stable across runs even when milliseconds are not.

## 4. The baseline: two different problems

Six of the eight queries were already fast (20–400 ms) and were dominated by
sequential scans feeding hash joins. Two were not:

- **Q03 took 2.5 minutes.** The plan is a nested loop with 8,023 outer orders,
  and each iteration sequentially scans all 181,512 payments to find the latest
  one: 1.46 billion rows examined, 15.2 million buffer touches.
- **Q06 took 1.3 seconds.** No ridiculous plan shape — 440k order lines joined
  to 21k variants and grouped — just a lot of unavoidable work, plus a 2.6 MB
  sort that spilled to disk.

That distinction drives the whole analysis. Q03 has a *missing access path*;
Q06 has a *workload* that an index can only partly reduce. Treating them the
same way would be the mistake.

---

## 5. Index design

| Index | Serves | Shape | Why |
|---|---|---|---|
| `ix_order_date (order_date) INCLUDE (status, grand_total)` | Q01, Q02, Q03 | B-tree, covering | Range predicate, and everything the report reads is in the leaf pages |
| `ix_payment_order_recent (order_id, created_at DESC) INCLUDE (payment_id)` | Q03 | B-tree, composite | Equality on `order_id`, then a backward walk to satisfy `ORDER BY … LIMIT 1` |
| `ix_order_customer (customer_id) INCLUDE (status, grand_total, order_date)` | Q07 (and Q04) | B-tree, covering | Groups by customer and needs three more columns; also the missing FK index |
| `ix_order_line_variant (variant_id) INCLUDE (line_total, quantity)` | Q02, Q06 | B-tree, covering | Revenue roll-ups walk from variants into lines; also the missing FK index |
| `ix_stock_movement_sales (warehouse_id, created_at) INCLUDE (variant_id, delta) WHERE reason = 'sale'` | Q05 | partial + covering | Equality, then range; restock rows are 7% of the ledger and never counted |
| `ix_product_category_category (category_id, product_id)` | Q06 | composite | The reverse of the `(product_id, category_id)` primary key |

Column order follows one rule: **equality predicates first, range second,
output-only columns in `INCLUDE`**. `ix_stock_movement_sales` is the clearest
case — had it been `(created_at, warehouse_id)` the range would stop the scan
from using the second column at all.

Two of these also repair genuine omissions from Portfolio 1: `order_line.variant_id`
and `customer_order.customer_id` are foreign keys with no index, so deleting a
single variant or customer had to scan the whole child table to enforce
`RESTRICT`.

## 6. Results

| # | Query | Before | After | Change | Pages before → after | What changed |
|---|---|---|---|---|---|---|
| Q01 | daily trading | 21.7 ms | **3.5 ms** | 6.2× | 2,403 → 56 | seq scan → index-only scan |
| Q02 | top products | 402 ms | **139 ms** | 2.9× | 5,984 → 4,018 | order selection by index, join strategy unchanged |
| Q03 | latest payment | **147,910 ms** | **27 ms** | **5,455×** | 15,166,425 → 31,491 | 181k-row scan per order → index probe per order |
| Q04 | never ordered | 79.9 ms | 45.2 ms | — | 3,021 → 3,021 | **no plan change**, index unused (noise) |
| Q05 | stock cover | 108 ms | **17.4 ms** | 6.2× | 4,030 → 588 | ledger scan → partial covering index |
| Q06 | category revenue | 1,318 ms | **701 ms** | 1.9× | 3,481 → 66,494 | hash joins → nested loop over index |
| Q07 | customer LTV | 312 ms | **198 ms** | 1.6× | 3,021 → 1,955 | heap scan → index-only scan |
| Q08 | carrier delivery | 64.9 ms | 55.1 ms | — | 1,729 → 1,729 | **no plan change**, index rejected (section 9) |

Total for all eight queries: **150.2 s → 1.19 s**. Excluding Q03, 2.31 s → 1.16 s.

Three different kinds of win, which is the point of running eight queries rather
than one:

1. **The access path disappears** (Q01, Q05). The plan stops reading a table at
   all: Q01 goes from a 2,400-page sequential scan to a 56-page index-only scan
   with `Heap Fetches: 0`.
2. **The plan shape stays, the cost per iteration collapses** (Q03, section 7).
3. **The join strategy changes but the aggregate still dominates** (Q02, Q06,
   Q07). These are honest, modest 1.6–2.9× improvements: the query has to
   aggregate 180k–440k rows and no index removes that.

And two non-results, kept in the table rather than quietly dropped: **Q04 and
Q08 did not get faster.** Their plans are byte-for-byte the same before and
after, their page counts are identical (Q04: 3,021 both times; Q08: 1,729), so
the small differences in milliseconds are measurement noise. Reporting them as
"1.8× and 1.2× faster" would have been dishonest.

## 7. Q03: the 2.5-minute query

Before — one sequential scan of the payment table per order:

```
 Nested Loop Left Join  (actual time=80.453..147901.669 rows=8023 loops=1)
   Buffers: shared hit=15166425
   ->  Index Scan using customer_order_pkey on customer_order o (rows=8023)
   ->  Limit  (actual time=18.415..18.416 rows=1 loops=8023)
         ->  Seq Scan on payment p  (actual time=18.027..18.370 rows=1 loops=8023)
               Filter: (order_id = o.order_id)
               Rows Removed by Filter: 181511
```

After — the same nested loop, with the inner step replaced by one index probe:

```
 Nested Loop Left Join  (actual time=0.162..17.989 rows=8023 loops=1)
   Buffers: shared hit=31449
   ->  Index Scan using ix_order_date on customer_order o (rows=8023)
   ->  Limit  (actual time=0.002..0.002 rows=1 loops=8023)
         ->  Incremental Sort  (Presorted Key: p.created_at)
               ->  Index Scan using ix_payment_order_recent on payment p
                     Index Cond: (order_id = o.order_id)   (rows=1 loops=8023)
```

The arithmetic is the whole story: **8,023 × 181,512 = 1.46 billion** row
visits became **8,023 index probes**, each returning the handful of payments for
one order. 15.2 million buffer touches became 31 thousand.

Note that the *plan shape did not change* — it is still a nested loop. What
changed is the cost of one iteration, from about 1,890 pages to about 4. This
is why "look for the Seq Scan inside a Nested Loop" is the first thing to
check: a sequential scan on the inner side of a nested loop is almost always a
missing index, and it degrades with the product of both tables' sizes rather
than their sum.

`Incremental Sort` appears because the index supplies `created_at DESC` already
ordered, so only the `payment_id` tie-break needs sorting within each group.

## 8. Q06: more pages, less time

Q06 is the exception that shows why "buffers went down" is not a goal:

| | Before | After |
|---|---|---|
| Time | 1,318 ms | 701 ms |
| Pages touched | 3,481 | 66,494 |

The new plan is 20× more page touches and 1.9× faster. The reason is that the
count mixes very different things. The old plan read 440k order lines
sequentially — few pages, cheap, prefetchable — but then built two hash tables
and sorted 440k rows. The new plan makes 21,560 index probes that each read a
run of adjacent leaf pages, then aggregates with an incremental sort. The extra
pages are *hits* (shared memory, ~0.1 µs each), not I/O: `shared read` was 32
pages for the whole query. The work that disappeared was CPU, not I/O.

The honest conclusion for Q06 is that the index helped less than any other in
the set, and the real fix would be a different one — see section 11.

## 9. What I tried and rejected

Three measurements in `experiments/`, all with raw output in `results/`:

**A plain index on `status` (`experiments/01`).** The hypothesis was that
`customer_order.status` appears in four of the eight queries, so it deserved an
index. It does — but only for rare values. `status = 'paid'` (7% of rows) uses a
bitmap index scan and takes 7 ms; `status = 'delivered'` (70%) is planned as a
sequential scan and takes 33 ms. Every query in this portfolio filters on a
*set* of statuses covering ~90% of the table, so the 1.4 MB index would sit
unused while still being maintained on every insert. Rejected.

**A covering index on `shipment` (`experiments/03`).** The candidate was
`(carrier) INCLUDE (dispatched_at, delivered_at) WHERE status = 'delivered'`,
meant to turn Q08 into an index-only scan. The planner ignored it and the
runtime did not move: Q08 needs ~90% of the table's rows, so any index path
visits almost as many pages as the heap, in random order instead of sequential.
6 MB of index for nothing. It was removed from `indexes.sql`, and Q08 is
reported as unchanged in section 6.

**Raising `work_mem` (`experiments/02`).** Q07 must aggregate 200k rows into
48,593 groups; the guess was that 4 MB was causing a spill. There was no spill
at either setting, and 64 MB made the query **slower** — 240 ms against 186 ms —
because the planner switched from `GroupAggregate` to `HashAggregate` with a
30 MB hash table. The old plan was grouping input that the index-only scan
already delivered sorted by `customer_id`, so the grouping cost no sort at all;
the extra memory bought a plan that throws that ordering away. This is the
clearest example in the portfolio of a tuning knob that is not a free win.

## 10. What the indexes cost

| Index | Size |
|---|---|
| `ix_stock_movement_sales` | 15 MB |
| `ix_order_line_variant` | 13 MB |
| `ix_order_customer` | 9.6 MB |
| `ix_order_date` | 9.2 MB |
| `ix_payment_order_recent` | 7.2 MB |
| `ix_product_category_category` | 264 kB |
| **Total** | **54 MB** on a 208 MB database (+26%) |

Building all six took 13.0 s and 8.7 s in two runs (`results/index_build_time_run1.txt`,
`run2.txt`) — a one-off cost, but one that would scale with the table size and
would need `CREATE INDEX CONCURRENTLY` on a live system to avoid blocking writes.

The cost that does not show up in a benchmark is write amplification: every
insert into `order_line` now maintains two B-trees instead of one, and every
update to `order_line.quantity` or `line_total` moves index entries that are
otherwise never read. That is the trade the six indexes justify only because
each one is tied to a query — the rejected `status` and `shipment` indexes in
section 9 are exactly what "index everything that appears in a WHERE clause"
produces.

## 11. Limitations and what I would do next

- **The dataset fits in RAM.** 208 MB against a 128 MB `shared_buffers` means
  most "I/O" in these plans is a buffer hit. On a 100× database the same plans
  would be I/O bound, and the index-driven plans would win by much more than
  the ratios above — the Q03 result (1.46 billion row visits eliminated) is the
  one that scales, because it was CPU-bound and structural, not cache-bound.
- **Q08 needs pre-aggregation, not an index.** A nightly `shipment_daily` fact
  table (carrier, date, count, avg transit days, on-time count) would turn a
  149k-row aggregate into a 365-row lookup. That belongs to the design, not to
  indexing.
- **Q06 needs a partitioned or pre-rolled `order_line`.** Grouping 440k lines to
  produce 8 numbers is the real problem; a materialised monthly revenue view
  refreshed after load would answer it in milliseconds.
- **Next experiment:** load the same seed at `SCALE=5` (`python seed.py 5.0`) and
  re-run `capture_plans.sh` to see which of these plans degrade linearly and
  which degrade with the product of the table sizes. The Q03 arithmetic predicts
  the latter would become unusable while the indexed form stays flat.

## 12. Reproducing

```bash
# from the repository root, with the database loaded as in Portfolio 1
cd portfolio-2-query-optimisation

psql -d shopstack -f drop_indexes.sql
./capture_plans.sh before          # writes plans/before/ and results/timings.csv

psql -d shopstack -f indexes.sql
./capture_plans.sh after           # appends to results/timings.csv

psql -d shopstack -f experiments/01_low_cardinality_status.sql
psql -d shopstack -f experiments/02_work_mem_sort.sql
psql -d shopstack -f experiments/03_rejected_shipment_index.sql
```

`capture_plans.sh` honours `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` and
`PSQL_BIN`, and falls back to the portable cluster at `../../.pg16` used to
build this portfolio (which listens on port 5433 — add `-p 5433` to the `psql`
commands above if that is the cluster you are using). Running the whole set
takes about ten minutes, almost all of it the 2.5-minute Q03 baseline repeated
four times.

On Windows, `psql`'s aligned output can fail on very wide result sets
(`could not print result table`) — the query still ran. Add `-A` for unaligned
output when running Q03 outside the capture script.

## 13. Reflection

The lesson I did not expect was how much of this activity was about measurement
rather than SQL. The first before/after comparison was wrong because building
the indexes had warmed the cache, and two queries looked 2–4× faster with
identical plans; the second attempt was wrong because `grep` was counting
`temp read=` as shared I/O. Both errors made the index set look better than it
was, which is the direction that is easiest to accept and therefore the one to
check hardest.

The result I trust most is Q03, because it does not depend on milliseconds: a
plan that examines 1.46 billion rows cannot be improved by a faster laptop. The
result I trust least is the 1.6× on Q07, which is within the run-to-run spread
and which section 9 shows is sensitive to a single planner parameter.
