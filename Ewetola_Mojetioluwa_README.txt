WHAT THIS SUBMISSION IS
-----------------------
One case study taken through the five portfolio activities. The case study is
ShopStack, a fictional online retailer trading in the UK, EU and US. The same
deterministic dataset is used throughout: 26 tables and 1.35 million rows,
regenerated by seed.py with a fixed random seed, so every plan and timing in the
documentation can be reproduced.

Each activity starts from the database the previous one left behind. Portfolio 2
optimises the schema designed in Portfolio 1; Portfolio 3 races sessions against
the data Portfolio 2 indexed; Portfolio 4 compares a document model of the same
catalogue against its relational original; Portfolio 5 distributes the database
across three regional shards with a streaming standby and a foreign-data-wrapper
router.


WHAT EACH FOLDER CONTAINS
-------------------------
portfolio-1-database-design/
  schema.sql (26 tables, keys, constraints, reconciliation view), ER diagrams in
  Chen and crow's-foot notation, seed.py, verify_seed.py, load.sql, checks.sql,
  captured verification output, and a README with the normalisation argument.

portfolio-2-query-optimisation/
  Eight business queries, six secondary indexes, before/after EXPLAIN
  (ANALYZE, BUFFERS) plans, timings.csv, three experiments, and a README
  explaining each plan change and each index that was rejected.

portfolio-3-transactions-concurrency/
  Commit, rollback and savepoint demonstrations; four two-session races (lost
  update, isolation levels, deadlock, write skew); captured psql transcripts and
  a README analysing each outcome.

portfolio-4-nosql/
  A 10,000-product MongoDB document model with its design rationale, five MQL
  queries and five SQL equivalents, three indexes, before/after
  explain("executionStats") output, three experiments, comparison.md covering
  key-value, wide-column and graph models, and a README.

portfolio-5-distributed-cloud/
  Three jurisdiction shards on ports 5441-5443, a physical streaming standby on
  5444, a postgres_fdw router on 5433, seven experiments (including node loss and
  a two-phase-commit probe), topology.md, cap-analysis.md, benchmarks and
  captured evidence.

documentation/
  The source of the submitted 2-3 page document.


HEADLINE RESULTS
----------------
Portfolio 2  Latest-payment query 147,910 ms -> 27 ms (5,455x); daily trading
             21.7 -> 3.5 ms; two indexes measured and deliberately rejected.
Portfolio 3  Two paid orders from one unit of stock, with no constraint error,
             because both sessions decided on a stale read; two fixes measured.
             Write skew survives REPEATABLE READ; SERIALIZABLE returns 40001.
Portfolio 4  Product page assembly 14.3 -> 3 ms in MongoDB; the brand league
             table is 4x slower there (22 vs 95 ms) because every array must be
             unwound.
Portfolio 5  Point lookup 0.66 ms routed vs 1.95 ms fanned out; count(*) 196.9 ms
             through the fan-out view vs 10.1 ms with per-shard partial
             aggregates; 63.3% of stock movements reference an order on another
             shard, reconciled by the router with 0 orphans.


HOW TO RUN
----------
Requirements: Python 3.9+, PostgreSQL 15+ (16.15 used here). Portfolio 4 also
needs MongoDB 7+ (9.0.4 used) and pymongo; Portfolio 5 needs no extra software.

  cd portfolio-1-database-design
  createdb -h localhost -p 5433 -U postgres shopstack
  psql -h localhost -p 5433 -U postgres -d shopstack -f schema.sql
  python seed.py && python verify_seed.py
  psql -h localhost -p 5433 -U postgres -d shopstack -f load.sql
  psql -h localhost -p 5433 -U postgres -d shopstack -f checks.sql

Then each activity's own scripts. The root README documents four alternative
routes (including portable binaries with no administrator rights) and the extra
steps for MongoDB and for the Portfolio 5 cluster.

The generated CSV files are not included: they total about 100 MB and are fully
reproducible from seed.py. The generator, not the data dump, is the artefact.
